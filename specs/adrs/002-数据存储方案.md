# ADR-002:使用SQLite存储日报历史

## 状态
已采纳

## 背景
虽然proposal.md明确要求“数据存储：本地SQLite”，但未来确保架构的合理性，需要对这一选择进行正式评估，确认其是否符合本场景。

## 选项

| 选项 | 优点 | 缺点 |
| ---- | ---- | ---- |
| SQLite | 零部署、零运维、Python内置支持、文件级备份 | 不支持高并发写入、数据量极大时查询性能下降 |
| PostgreSQL | 功能完备、支持高并发、强大的全文搜索能力 | 需要独立部署和运维、对5人团队日报场景而言过于沉重 |
| JSON文件 | 实现最简单、不需要任何部署 | 缺乏复杂查询能力、并发写入不完全、数据量增长后难以管理 |

## 决策
使用SQLite

## 理由
1. proposal.md明确决定运行方式为“定时任务，不需要常驻服务”，这意味着不存在并发写入场景（）每天仅执行一次）。
2. 5人团队一年的日报数据约为1250条，SQLite处理起来绰绰有余。
3. 零运维高度符合项目定位——我们不想为了一个简单的日报工具去维护一个独立的数据库服务。
4. Python标准库sqlite3开箱即用，不需要引入额外的第三方依赖。
